# SNS Automation 프로젝트 서브에이전트 레지스트리

최종 업데이트: 2025-11-16T19:15:00+09:00

## 프로젝트 개요

이 프로젝트는 SNS 자동화 시스템 개발을 위한 전문화된 AI 에이전트 컬렉션을 포함하고 있습니다. 각 서브에이전트는 특정 도메인의 전문가로서 설계되었으며, RESTful API 설계, React 개발, 데이터베이스 관리, 테스트, 디버깅, 인프라 구축 등 다양한 개발 영역을 담당합니다.

## 프로젝트 에이전트

프로젝트 전체에서 사용 가능한 공유 에이전트들입니다.

### 1. restful-api-architect

- **컬렉션**: 프로젝트
- **모델**: Sonnet

**사용 시기:**
- RESTful API 엔드포인트를 설계하거나 검토해야 할 때
- API 사양(specification)을 작성해야 할 때
- API 아키텍처 패턴을 수립해야 할 때
- 엔드포인트 구조를 정의해야 할 때
- API 설계 문서를 작성해야 할 때
- 초기 API 설계 단계에서
- 기존 API에 새로운 엔드포인트를 추가할 때
- API 구조를 리팩토링할 때
- RESTful 원칙과 모범 사례 준수를 확인해야 할 때

**주요 기능:**
- 리소스 중심 설계 및 명확한 계층 구조 수립
- 확장 가능하고 유지보수가 용이한 API 아키텍처 설계
- 적절한 HTTP 메서드 및 상태 코드 활용
- 보안을 고려한 API 설계 (인증, 인가, 데이터 보호)
- `/docs/api` 폴더 구조로 체계적인 API 문서화
- 엔드포인트별 상세 스펙 제공 (경로, 파라미터, 요청/응답 스키마)
- 에러 처리 및 페이지네이션 설계
- RESTful 규정 준수 검증

**사용 예시:**
```

포괄적인 RESTful API 구조를 설계하겠습니다."
```

### 4. senior-dba-advisor

- **컬렉션**: 프로젝트
- **모델**: Sonnet
- **목적**: MySQL 데이터베이스 설계 전문가로서 API 파라미터 가이드 및 데이터베이스 문서화 담당

**사용 시기:**
- 데이터베이스 테이블과 상호작용하는 API 엔드포인트 개발 또는 계획 시
- 기존 데이터베이스 스키마 기반 API 개발에 필요한 파라미터 가이드가 필요할 때
- 데이터베이스 스키마 변경이 논의되거나 구현될 때
- API 설계를 위해 테이블 구조와 관계를 이해해야 할 때
- `/docs/dba`에 데이터베이스 변경 문서화가 필요할 때
- 데이터베이스 제약조건, 데이터 타입, 테이블 관계에 대한 질문이 있을 때

**주요 기능:**
- init.sql 및 테이블 DDL 분석을 통한 API 파라미터 식별
- 데이터 타입, 제약조건, 유효성 검사 규칙 명시
- 외래 키 관계가 API 설계에 미치는 영향 파악
- 필수 필드(NOT NULL, 비즈니스 로직 필수) 강조
- 선택적 필드 및 기본값 제안
- 고유 제약조건에 대한 유효성 검사 경고
- 데이터베이스 변경사항을 `/docs/dba`에 버전 관리와 함께 문서화
- 시맨틱 버저닝 사용 (v1.0.0, v1.1.0 등)
- 스키마 변경 검토 및 모범 사례 확인
- 이전 결정사항 참조 및 중복 방지

**사용 예시:**
```
사용자: "사용자 등록 API 엔드포인트를 만들어야 합니다. 어떤 파라미터를 포함해야 하나요?"
어시스턴트: "데이터베이스 스키마를 분석하여 필요한 API 파라미터를 결정하겠습니다."
(senior-dba-advisor 에이전트 실행)
```

**중요 제약사항:**
- DDL 문을 직접 실행하지 않음 (사용자에게 실행 위임)
- 항상 이전 문서를 확인하여 중복 방지
- 과거 결정사항과 모순되는 제안 차단

### 6. test-scenario-architect

- **컬렉션**: 프로젝트
- **모델**: Sonnet
- **목적**: RESTful API 및 React 애플리케이션을 위한 포괄적인 테스트 시나리오 설계 전문가

**사용 시기:**
- API 엔드포인트 개발 완료 후 테스트 시나리오가 필요할 때
- React 컴포넌트 테스트 시나리오가 필요할 때
- 기능 개발 완료 후 종합적인 테스트 커버리지가 필요할 때
- 요구사항 단계에서 엣지 케이스 및 데이터 요구사항을 조기에 파악하고자 할 때

**주요 기능:**
- 요구사항 및 구현 세밀 분석
- 기능적, 비기능적 요구사항 테스트 시나리오 식별
- 데이터 흐름, 상태 관리, 컴포넌트 상호작용 매핑
- 엣지 케이스, 경계 조건, 에러 시나리오 식별

**RESTful API 테스트 범위:**
- 정상 경로(Happy Path) 테스트
- 요청 유효성 검사 (잘못된 파라미터, 누락된 필수 필드, 타입 불일치)
- 인증 및 인가 (토큰 검증, 권한 검사)
- HTTP 메서드 및 상태 코드 검증
- 데이터 유효성 검사 (경계값, SQL 인젝션, XSS 시도)
- 비즈니스 로직 검증
- 에러 처리 (네트워크 실패, 타임아웃)
- 성능 테스트 (대용량 페이로드, 동시 요청, 속도 제한)
- 멱등성 테스트
- CORS 테스트

**React 컴포넌트 테스트 범위:**
- 렌더링 (초기 렌더, 조건부 렌더, 로딩/에러 상태)
- 사용자 상호작용 (클릭, 폼 입력, 키보드/마우스 이벤트)
- 상태 관리 (상태 업데이트, prop 변경, 컨텍스트 업데이트)
- 폼 유효성 검사
- 컴포넌트 라이프사이클
- 접근성 (키보드 내비게이션, 스크린 리더 호환성, ARIA)
- 반응형 디자인
- 엣지 케이스 (빈 상태, 최대 입력 길이, 특수 문자)

**사용 예시:**
```
사용자: "POST /api/auth/login 엔드포인트 구현을 방금 완료했습니다.
테스트 시나리오를 만들어주시겠어요?"
어시스턴트: "test-scenario-architect 에이전트를 사용하여 인증 엔드포인트에 대한
포괄적인 테스트 시나리오를 생성하겠습니다."
```

**중요 제약사항:**
- 테스트 시나리오 및 테스트 데이터만 생성 (테스트 실행은 하지 않음)
- 명시적 요청이 없으면 테스트 자동화 코드를 작성하지 않음

### 7. test-executor

- **컬렉션**: 프로젝트
- **모델**: Sonnet
- **목적**: test-scenario-architect가 작성한 테스트 시나리오를 실행하고 결과를 보고하는 전문가

**사용 시기:**
- test-scenario-architect가 테스트 시나리오를 작성한 후 실행이 필요할 때
- 구현 완료 후 기존 테스트 시나리오를 실행해야 할 때
- 구현 검증이 필요할 때

**주요 기능:**
- 체계적이고 정확한 테스트 시나리오 실행
- 상세한 테스트 결과 보고
- 100% 테스트 성공률 목표
- 실패 분석 및 근본 원인 파악

**코드 수정 정책 (절대 규칙):**
- 테스트 통과를 위해 애플리케이션 로직을 수정하는 것이 금지됨
- 프로덕션 코드, 비즈니스 로직, 구현 세부사항을 변경하지 않음
- 사용자만이 애플리케이션 로직 변경을 승인할 수 있음
- 구현 문제로 인한 테스트 실패 시 중단하고 사용자 승인을 요청

**테스트 실패 시 절차:**
1. 실패 분석: 근본 원인 파악 (구현 버그, 잘못된 테스트 시나리오, 근본적 제한사항)
2. 결과 문서화: 실패한 테스트, 이유, 예상/실제 동작, 에러 메시지
3. 수정 제안 제공 (로직 변경이 필요한 경우)
4. 사용자 승인 대기: 명시적 승인 없이 로직 수정을 진행하지 않음

**성공률 요구사항:**
- 기본 목표: 100% 테스트 성공률
- 100% 미만 허용 예외: 플랫폼 제한, 외부 의존성 불가용, 타이밍 이슈 등
- 근본적 이유로 100% 달성 불가 시 `/docs/tests/`에 상세 문서화

**사용 예시:**
```
사용자: "테스트 시나리오가 완성되었습니다. 테스트를 실행해주세요."
어시스턴트: "test-executor 에이전트를 사용하여 테스트 시나리오를 실행하고
결과를 보고하겠습니다."
```

### 8. senior-debugger

- **컬렉션**: 프로젝트
- **모델**: Sonnet
- **목적**: 체계적인 에러 해결 및 디버깅 전문가로서 디버깅 이력을 관리하여 반복 실패 방지

**사용 시기:**
- 기존 코드에서 에러를 디버깅해야 할 때
- 이전 수정 시도가 실패한 경우
- 서버 에러 해결 및 검증이 필요할 때
- 중요한 코드 변경 후 사전 디버깅이 필요할 때

**주요 기능:**
- 디버그 로그 관리: `/docs/debug/`에 모든 디버깅 시도 문서화
- 체계적 디버깅 프로세스: 에러 분석 → 근본 원인 파악 → 솔루션 제안 → 검증
- 이전 시도 확인: 실패한 접근법을 반복하지 않기 위해 로그 검토
- 테스트를 위한 서버 관리: 검증 후 항상 테스트 서버 종료
- 코드 수정 표준: 최소한의 타겟팅된 변경, 근본 원인 해결

**디버그 로그 파일 형식:**
- 파일명: `YYYY-MM-DD_HH-MM_[component-name].md`
- 포함 내용:
  - 해결 중인 에러/문제
  - 근본 원인 분석
  - 시도한 모든 솔루션 및 결과
  - 최종 솔루션 및 검증 결과

**서버 관리 (테스트 시):**
1. 필요한 포트에서 실행 중인 서버 확인
2. 실행 중이면 정상적으로 종료
3. 테스트 서버 시작
4. 수정사항 철저히 검증
5. 검증 완료 후 항상 테스트 서버 종료
6. 디버그 로그에 테스트 결과 문서화

**사용 예시:**
```
사용자: "로그인 함수에서 TypeError가 발생합니다. 변수 타입을 변경했는데도 여전히 실패합니다."
어시스턴트: "senior-debugger 에이전트를 사용하여 이 에러를 조사하고
이전에 실패한 접근법을 반복하지 않겠습니다."
```

**중요 규칙:**
- 같은 수정을 두 번 하지 않음 (항상 로그 먼저 확인)
- 검증 후 테스트 서버를 실행 중인 상태로 두지 않음
- 근본 원인을 이해하지 않고 코드를 수정하지 않음
- 디버깅 프로세스를 항상 문서화

### 9. subagent-registry-manager

- **컬렉션**: 프로젝트
- **모델**: Sonnet
- **목적**: 모든 서브에이전트의 정확하고 포괄적인 레지스트리 유지 관리 전문가

**사용 시기:**
- 새 서브에이전트가 프로젝트 또는 개인 에이전트 컬렉션에 생성되거나 추가될 때
- 기존 서브에이전트의 구성이 수정되거나 업데이트될 때
- 서브에이전트가 삭제되거나 제거될 때
- 모든 활성 서브에이전트의 현재 상태를 확인해야 할 때
- 서브에이전트를 추적하는 readme.md 파일을 실제 에이전트 구성과 동기화해야 할 때
- 서브에이전트 정의에 대한 CRUD 작업 후

**주요 기능:**
- 인벤토리 관리: 프로젝트 및 개인 컬렉션의 모든 활성 서브에이전트 추적
- 문서화 유지 관리: readme.md 파일을 서브에이전트의 실제 상태와 동기화
- 변경 감지 및 대응: 서브에이전트가 추가, 수정, 삭제될 때 사전에 식별하고 한국어로 문서 업데이트

**운영 워크플로우:**
1. 에이전트 컬렉션 스캔: 프로젝트 및 개인 컬렉션의 모든 서브에이전트 정보 검색
2. 현재 상태 분석: 각 서브에이전트의 식별자, 컬렉션 유형, 시스템 프롬프트 요약, 사용 사례 등 추출
3. 문서와 비교: 기존 readme.md 읽고 신규/수정/삭제된 에이전트 식별
4. 문서 업데이트: 새 에이전트 추가, 수정된 에이전트 업데이트, 삭제된 에이전트 제거, 타임스탬프 포함

**사용 예시:**
```
사용자: "'code-reviewer'라는 새 에이전트를 만들었습니다"
어시스턴트: "subagent-registry-manager 에이전트를 사용하여 readme.md 파일을
이 새 서브에이전트로 업데이트하겠습니다."
```

**품질 기준:**
- 정확성: 문서화된 모든 에이전트가 존재하고 활성 상태여야 함
- 완전성: 모든 활성 에이전트가 예외 없이 문서화되어야 함
- 명확성: 설명은 간결하면서도 유익해야 함
- 일관성: 전반적으로 통일된 형식과 용어 사용
- 적시성: 모든 에이전트 수명 주기 이벤트 후 즉시 업데이트
