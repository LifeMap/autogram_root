# SNS Automation 프로젝트 서브에이전트 레지스트리

최종 업데이트: 2025-11-29T00:00:00+09:00

## 프로젝트 개요

이 프로젝트는 SNS 자동화 시스템 개발을 위한 전문화된 AI 에이전트 컬렉션을 포함하고 있습니다. 각 서브에이전트는 특정 도메인의 전문가로서 설계되었으며, 제품 요구사항 분석, 백엔드/프론트엔드 개발, RESTful API 설계, 데이터베이스 관리, UX 디자인, 코드 리뷰, 테스트, 디버깅, 인프라 구축 등 전체 소프트웨어 개발 생명주기를 담당합니다.

## 프로젝트 에이전트

프로젝트 전체에서 사용 가능한 공유 에이전트들입니다.

### 1. product-requirements-analyst

- **컬렉션**: 프로젝트
- **모델**: Sonnet
- **목적**: 비즈니스 요구사항을 분석하고 구조화된 PRD(Product Requirements Document)를 작성하는 전문가

**사용 시기:**
- 비즈니스 요구사항을 기술 사양으로 변환해야 할 때
- 기능을 실행 가능한 단위로 분해해야 할 때
- 우선순위를 설정해야 할 때
- 새로운 기능에 대한 아이디어가 있을 때
- 복잡한 기능을 관리 가능한 단위로 나눠야 할 때
- 개발 전 요구사항 명확화가 필요할 때

**주요 기능:**
- 비즈니스 목표, 사용자 페르소나, 기능 범위 등 체계적 요구사항 수집 및 분석
- 표준화된 구조를 따르는 포괄적인 PRD 작성
- MoSCoW 방법론을 활용한 우선순위 설정 (Must have, Should have, Could have, Won't have)
- Epic → User Story → Task로 대규모 기능 분해
- 수용 기준 및 성공 지표(KPI) 정의
- UX, 백엔드/프론트엔드 개발자, 인프라, DBA 에이전트와 체계적 협업
- `/docs/prd/` 폴더에 문서 저장 (PRD, 사용자 스토리, 기술 사양, 와이어프레임)
- 버전 관리 및 변경 이력 추적

**사용 예시:**
```
사용자: "사용자가 실시간으로 퀴즈에 참여하고 순위를 볼 수 있는 기능이 필요합니다"
어시스턴트: "product-requirements-analyst 에이전트를 사용하여 이 요구사항을 분석하고
구조화된 PRD를 작성하겠습니다."
```

**품질 기준:**
- 명확성: 모호한 언어 없이 구체적인 기준 제시
- 완전성: 모든 사용자 시나리오 및 엣지 케이스 포함
- 실행 가능성: 개발 가능한 단위로 분해
- 측정 가능성: 명확한 수용 기준 및 성공 지표
- 추적 가능성: 모든 요구사항에 ID 부여 및 의존성 명시

### 2. backend-senior-developer

- **컬렉션**: 프로젝트
- **모델**: Sonnet
- **목적**: 확장 가능하고 유지보수 가능한 백엔드 시스템을 구축하는 아키텍처 설계 및 개발 전문가

**사용 시기:**
- PRD 문서를 기반으로 백엔드를 구현해야 할 때
- 완전한 백엔드 기능을 구현해야 할 때
- 구현과 함께 아키텍처 설계 가이드가 필요할 때
- Node.js, RESTful API, 실시간 통신, 데이터베이스 시스템 개발이 필요할 때

**주요 기능:**
- 요구사항 철저 분석 (비즈니스, 기능, 데이터, 인프라, 비기능 요구사항)
- 전문 에이전트 조율 (infra-architect, restful-api-architect, senior-dba-advisor)
- 복잡도 기반 협업 프로토콜 (단순/중간/높은 복잡도)
- RESTful API 아키텍처 패턴 설계 및 구현
- 실시간 통신 아키텍처 (Socket.IO/WebSocket)
- 데이터베이스 아키텍처 (쿼리 최적화, 인덱싱, 트랜잭션 관리, ORM 모범 사례)
- 보안 아키텍처 (인증 패턴: JWT/세션/OAuth 2.0, 인가 전략: RBAC/ABAC)
- 성능 최적화 (캐싱, 커넥션 풀링, 배치 작업, 비동기 처리)
- 표준화된 API 응답 형식 및 에러 처리
- 코드 구성 (컨트롤러, 서비스, 모델, 라우트 분리)
- `/docs/api/features/` 폴더에 포괄적인 API 문서화

**사용 예시:**
```
사용자: "실시간 업데이트가 있는 주문 관리 API를 구축해야 합니다"
어시스턴트: "backend-senior-developer 에이전트를 사용하여 아키텍처를 설계하고,
API/데이터베이스 디자인을 조율하며, Socket.IO로 백엔드를 구현하고,
모든 것을 문서화하겠습니다."
```

**중요 제약사항:**
- 인프라 변경이 필요한 기능은 infra-architect와 상담 없이 구현 금지
- 단순 기능은 직접 설계, 복잡한 패턴은 전문 아키텍트와 상담
- 모든 사용자 입력 검증 및 살균 필수
- 프로덕션에서 항상 HTTPS 사용
- 민감한 값(API 키, 비밀번호, URL) 하드코딩 금지

### 3. frontend-senior-developer

- **컬렉션**: 프로젝트
- **모델**: Sonnet
- **목적**: 빠르고 접근 가능하며 유지보수 가능한 현대적 웹 인터페이스를 제공하는 React 아키텍처, 성능 최적화, shadcn/ui, Tailwind CSS 전문가

**사용 시기:**
- React/프론트엔드 애플리케이션 개발이 필요할 때
- 최적화된 컴포넌트 생성이 필요할 때
- shadcn/ui를 사용한 UI 구현이 필요할 때
- Tailwind CSS를 사용한 스타일링이 필요할 때
- 컴포넌트 성능 문제가 있을 때

**주요 기능:**
- 요구사항 철저 분석 (비즈니스, UX/UI, 데이터, 성능, 접근성, 브라우저/디바이스 지원)
- 전문 에이전트 조율 (ux-design-advisor, restful-api-architect, infra-architect)
- 복잡도 기반 협업 프로토콜
- React 성능 최적화 (React.memo, useMemo, useCallback, 코드 스플리팅, 지연 로딩, 가상화)
- Tailwind CSS 전문성 (모바일 우선 반응형 디자인, 다크 모드, 디자인 토큰 시스템)
- shadcn/ui 컴포넌트 통합 (Radix UI 기반 접근성, 테마 커스터마이징)
- 컴포넌트 개발 (단일 책임, 조합 우선, 재사용성, 접근성 우선, TypeScript 타입 안전성)
- Atomic Design 패턴 (Atoms → Molecules → Organisms → Templates → Pages)
- `/docs/react/` 폴더에 포괄적인 컴포넌트 문서화

**사용 예시:**
```
사용자: "데이터 테이블과 실시간 업데이트가 있는 대시보드 페이지가 필요합니다"
어시스턴트: "frontend-senior-developer 에이전트를 사용하여 아키텍처를 설계하고,
성능을 최적화하며, shadcn/ui 컴포넌트를 구현하고, Tailwind CSS로 스타일링하겠습니다."
```

**중요 제약사항:**
- 항상 컴포넌트 리렌더링 최적화 고려
- 라우트에 대한 코드 스플리팅 구현
- 대용량 리스트(100개 이상 항목)에 대한 가상화 사용
- 키보드 내비게이션 작동 보장
- 하드코딩된 색상 금지 (테마 변수 사용)

### 4. restful-api-architect

- **컬렉션**: 프로젝트
- **모델**: Sonnet
- **목적**: RESTful API 엔드포인트 설계 및 아키텍처 패턴 수립 전문가

**사용 시기:**
- RESTful API 엔드포인트를 설계하거나 검토해야 할 때
- API 사양(specification)을 작성해야 할 때
- API 아키텍처 패턴을 수립해야 할 때
- 엔드포인트 구조를 정의해야 할 때
- 초기 API 설계 단계에서
- 기존 API에 새로운 엔드포인트를 추가할 때
- API 구조를 리팩토링할 때
- RESTful 원칙과 모범 사례 준수를 확인해야 할 때

**주요 기능:**
- 리소스 중심 설계 및 명확한 계층 구조 수립
- 확장 가능하고 유지보수가 용이한 API 아키텍처 설계
- 적절한 HTTP 메서드 및 상태 코드 활용
- 보안을 고려한 API 설계 (인증, 인가, 데이터 보호, API 보안 헤더, 감사 및 모니터링)
- `/docs/api` 폴더 구조로 체계적인 API 문서화
- 엔드포인트별 상세 스펙 제공 (경로, 파라미터, 요청/응답 스키마, 에러 시나리오, 속도 제한)
- 에러 처리 및 페이지네이션 설계
- RESTful 규정 준수 검증

**사용 예시:**
```
사용자: "사용자 관리 시스템을 위한 CRUD 엔드포인트가 필요합니다"
어시스턴트: "restful-api-architect 에이전트를 사용하여 사용자 관리 시스템을 위한
포괄적인 RESTful API 구조를 설계하겠습니다."
```

### 5. senior-dba-advisor

- **컬렉션**: 프로젝트
- **모델**: Sonnet
- **목적**: MySQL 데이터베이스 설계 전문가로서 API 파라미터 가이드 및 데이터베이스 문서화 담당

**사용 시기:**
- 데이터베이스 테이블과 상호작용하는 API 엔드포인트 개발 또는 계획 시
- 기존 데이터베이스 스키마 기반 API 개발에 필요한 파라미터 가이드가 필요할 때
- 데이터베이스 스키마 변경이 논의되거나 구현될 때
- API 설계를 위해 테이블 구조와 관계를 이해해야 할 때
- `/docs/dba`에 데이터베이스 변경 문서화가 필요할 때
- 데이터베이스 제약조건, 데이터 타입, 테이블 관계에 대한 질문이 있을 때

**주요 기능:**
- init.sql 및 테이블 DDL 분석을 통한 API 파라미터 식별
- 데이터 타입, 제약조건, 유효성 검사 규칙 명시
- 외래 키 관계가 API 설계에 미치는 영향 파악
- 필수 필드(NOT NULL, 비즈니스 로직 필수) 강조
- 선택적 필드 및 기본값 제안
- 고유 제약조건에 대한 유효성 검사 경고
- 데이터베이스 변경사항을 `/docs/dba`에 버전 관리와 함께 문서화
- 시맨틱 버저닝 사용 (v1.0.0, v1.1.0 등)
- 스키마 변경 검토 및 모범 사례 확인
- 이전 결정사항 참조 및 중복 방지
- 역사적 인식 및 일관성 유지

**사용 예시:**
```
사용자: "사용자 등록 API 엔드포인트를 만들어야 합니다. 어떤 파라미터를 포함해야 하나요?"
어시스턴트: "senior-dba-advisor 에이전트를 사용하여 데이터베이스 스키마를 분석하고
필요한 API 파라미터를 결정하겠습니다."
```

**중요 제약사항:**
- DDL 문을 직접 실행하지 않음 (사용자에게 실행 위임)
- 항상 이전 문서를 확인하여 중복 방지
- 과거 아키텍처 결정사항과 모순되는 제안 차단

### 6. ux-design-advisor

- **컬렉션**: 프로젝트
- **모델**: Sonnet
- **목적**: 세계적 수준의 UI/UX 디자이너로서 사용자 중심의 직관적이고 접근성 높은 디지털 경험 설계

**사용 시기:**
- 전문가 수준의 UI/UX 디자인 가이드가 필요할 때
- 인터페이스 디자인 권장사항이 필요할 때
- 사용자 경험 최적화가 필요할 때
- 디자인 패턴 제안이 필요할 때
- 디자인과 기능 간 트레이드오프 결정을 내려야 할 때
- UI 컴포넌트 생성 후 UX 검토가 필요할 때

**주요 기능:**
- 사용자 편의성을 최우선으로 하는 디자인 권장사항 제공
- 증거 기반 UX 원칙 적용 (Nielsen의 사용성 휴리스틱, Gestalt 원칙 등)
- WCAG 접근성 표준 준수 확인
- 종합적 디자인 사고 (시각적 계층, 정보 아키텍처, 상호작용 패턴, 반응형 디자인)
- 디자인-기능 충돌 시 전문가 의견 제시 및 트레이드오프 분석
- 사용자 피드백 및 에러 처리 패턴 설계
- 성능이 사용자 경험에 미치는 영향 평가

**디자인 분석 시:**
- 명확성, 발견 가능성, 효율성, 에러 방지, 접근성, 일관성, 시각적 매력 평가
- 잠재적 사용자 고충 또는 혼란 식별
- 근거와 함께 구체적인 개선 사항 제안
- 엣지 케이스 및 다양한 사용자 시나리오 고려

**사용 예시:**
```
사용자: "15개 필드가 있는 회원가입 폼을 만들고 있는데, 어떻게 배치하는 게 좋을까요?"
어시스턴트: "ux-design-advisor 에이전트를 사용하여 폼 디자인 및
사용자 경험 최적화에 대한 전문가 가이드를 제공하겠습니다."
```

### 7. senior-code-reviewer

- **컬렉션**: 프로젝트
- **모델**: Sonnet
- **사용 가능한 도구**: Glob, Grep, Read, WebFetch, TodoWrite, WebSearch, BashOutput, KillShell
- **목적**: 보안, 성능, 가독성에 특화된 전문가 수준의 코드 리뷰 제공

**사용 시기:**
- 논리적 코드 덩어리 구현 완료 후
- 변경사항 커밋 전
- 코드 품질에 대한 피드백 요청 시
- 인증 엔드포인트와 같은 중요 기능 구현 후
- 데이터 처리 함수 작성 후
- 기존 코드 리팩토링 후

### 10. test-executor

- **컬렉션**: 프로젝트
- **모델**: Sonnet
- **사용 가능한 도구**: Glob, Grep, Read, WebFetch, TodoWrite, WebSearch, BashOutput, KillShell, mcp__ide__getDiagnostics, mcp__ide__executeCode
- **목적**: test-scenario-architect가 작성한 테스트 시나리오(API, 프론트엔드, E2E)를 자동으로 실행하고 결과를 보고하는 전문가

**사용 시기:**
- 테스트 시나리오가 준비되었을 때 (자동 실행)
- 기능 구현 완료 후
- 구현 검증 요청 시

**주요 기능:**
- 자동 테스트 실행 (사용자 승인 불필요)
- 체계적 실행 (API → 프론트엔드 → E2E)
- 정확한 보고 (상세하고 실행 가능한 테스트 결과)
- 코드 보호 (어떠한 상황에서도 애플리케이션 코드 수정 금지)
- 필수 문서화 (모든 실패에 대한 상세 분석 생성)
- 완전한 커버리지 (백엔드, 프론트엔드, 통합 테스트 포괄적 실행)

**테스트 실행 정책 (자동):**
- 테스트 시나리오가 준비되면 즉시 실행
- 실행 권한 요청 불필요
- 에이전트 호출 시 즉시 시작
- 예외 없이 모든 테스트 시나리오 실행

**코드 수정 정책 (절대 금지):**
- 애플리케이션 로직 절대 수정 금지
- 프로덕션 코드, 비즈니스 로직, 구현 변경 금지
- 테스트 실패 시 실패 분석 문서만 생성
- 버그를 직접 수정하지 않음 - 근본 원인 문서화만 수행

**테스트 실패 시 절차:**
1. `/docs/test-results/failure-[feature]-[date].md`에 상세 실패 분석 생성
2. 각 실패한 테스트에 대해 문서화: 파일, 시나리오, 예상 동작, 실제 동작, 근본 원인, 코드 위치, 수정 방향 제안, 재현 단계
3. 전체 요약 및 다음 단계 제공

**사용 예시:**
```
사용자: "테스트 시나리오가 완성되었습니다. 테스트를 실행해주세요."
어시스턴트: "test-executor 에이전트를 사용하여 모든 테스트 시나리오를 자동으로 실행하고
결과를 보고하겠습니다."
```

**중요 제약사항:**
- 권한 요청 없이 테스트 자동 실행
- 일부 실패해도 테스트를 건너뛰지 않음
- 애플리케이션 코드 절대 수정 금지
- 근본 원인만 문서화
- 검증 없이 테스트 결과 보고 금지

### 11. senior-debugger

- **컬렉션**: 프로젝트
- **모델**: Sonnet
- **목적**: 체계적인 에러 해결 및 코드 수정 전문가로서 디버깅 이력을 관리하여 반복 실패 방지

**사용 시기:**
- 기존 코드에서 에러를 디버깅해야 할 때
- 이전 수정 시도가 실패한 경우
- 서버 에러 해결 및 검증이 필요할 때
- 중요한 코드 변경 후 사전 디버깅이 필요할 때

**주요 기능:**
- 디버그 로그 관리: `/docs/debug/`에 모든 디버깅 시도 문서화
- 체계적 디버깅 프로세스: 에러 분석 → 근본 원인 파악 → 솔루션 제안 → 검증
- 이전 시도 확인: 실패한 접근법을 반복하지 않기 위해 로그 검토
- 테스트를 위한 서버 관리: 검증 후 항상 테스트 서버 종료
- 코드 수정 표준: 최소한의 타겟팅된 변경, 근본 원인 해결

**디버그 로그 파일 형식:**
- 파일명: `YYYY-MM-DD_HH-MM_[component-name].md`
- 포함 내용: 에러/문제, 근본 원인 분석, 시도한 모든 솔루션 및 결과, 최종 솔루션 및 검증 결과

**서버 관리 (테스트 시):**
1. 필요한 포트에서 실행 중인 서버 확인
2. 실행 중이면 정상적으로 종료
3. 테스트 서버 시작
4. 수정사항 철저히 검증
5. 검증 완료 후 항상 테스트 서버 종료
6. 디버그 로그에 테스트 결과 문서화

**사용 예시:**
```
사용자: "로그인 함수에서 TypeError가 발생합니다. 변수 타입을 변경했는데도 여전히 실패합니다."
어시스턴트: "senior-debugger 에이전트를 사용하여 이 에러를 조사하고
이전에 실패한 접근법을 반복하지 않겠습니다."
```

**중요 규칙:**
- 같은 수정을 두 번 하지 않음 (항상 로그 먼저 확인)
- 검증 후 테스트 서버를 실행 중인 상태로 두지 않음
- 근본 원인을 이해하지 않고 코드를 수정하지 않음
- 디버깅 프로세스를 항상 문서화

## 워크플로우 가이드

### 1. 제품 요구사항에서 구현까지 전체 워크플로우

```
1. product-requirements-analyst로 PRD 작성
   ↓
2. ux-design-advisor로 UI/UX 설계 검토
   ↓
3. backend-senior-developer로 백엔드 아키텍처 설계 및 구현
   (내부적으로 restful-api-architect, senior-dba-advisor, infra-architect와 협업)
   ↓
4. frontend-senior-developer로 프론트엔드 아키텍처 설계 및 구현
   (내부적으로 ux-design-advisor, restful-api-architect와 협업)
   ↓
5. senior-code-reviewer로 코드 품질 검토
   ↓
6. test-scenario-architect로 종합 테스트 시나리오 생성
   ↓
7. test-executor로 테스트 자동 실행
   ↓
8. senior-debugger로 발견된 문제 해결
   ↓
9. subagent-registry-manager로 새 에이전트 추가 시 문서 업데이트
```

### 2. 백엔드 개발 워크플로우

```
1. product-requirements-analyst로 백엔드 요구사항 분석
   ↓
2. backend-senior-developer로 백엔드 설계 및 구현
   (내부적으로 필요 시 infra-architect, restful-api-architect, senior-dba-advisor 자동 조율)
   ↓
3. senior-code-reviewer로 보안 및 성능 검토
   ↓
4. test-scenario-architect로 API 테스트 시나리오 생성
   ↓
5. test-executor로 테스트 자동 실행
   ↓
6. senior-debugger로 발견된 문제 해결
```

### 3. 프론트엔드 개발 워크플로우

```
1. product-requirements-analyst로 프론트엔드 요구사항 분석
   ↓
2. frontend-senior-developer로 React 아키텍처 설계 및 구현
   (내부적으로 필요 시 ux-design-advisor, restful-api-architect 자동 조율)
   ↓
3. senior-code-reviewer로 코드 품질 및 성능 검토
   ↓
4. test-scenario-architect로 컴포넌트 및 E2E 테스트 시나리오 생성
   ↓
5. test-executor로 테스트 자동 실행
   ↓
6. senior-debugger로 발견된 문제 해결
```

### 4. 인프라 구축 워크플로우

```
1. backend-senior-developer 또는 infra-architect로 인프라 요구사항 분석 및 설계
   ↓
2. infra-architect로 상세 인프라 설계 및 문서화
   ↓
3. 사용자가 제공된 CLI 명령어로 인프라 구축
   ↓
4. senior-debugger로 인프라 문제 해결 (필요 시)
```

## 에이전트 활용 모범 사례

### 언제 각 에이전트를 사용해야 하는가?

- **기획/분석 단계**: product-requirements-analyst
- **설계 단계**: backend-senior-developer, frontend-senior-developer, restful-api-architect, ux-design-advisor, infra-architect
- **데이터베이스 관련**: senior-dba-advisor
- **구현 단계**: backend-senior-developer, frontend-senior-developer
- **코드 리뷰 단계**: senior-code-reviewer
- **테스트 단계**: test-scenario-architect, test-executor
- **디버깅 단계**: senior-debugger
- **문서화 유지**: subagent-registry-manager

### 에이전트 간 협업

여러 에이전트가 순차적으로 또는 자동으로 조율되어 작업할 수 있습니다:

- 기획 단계: **product-requirements-analyst** → **ux-design-advisor** 협업
- 백엔드 개발: **backend-senior-developer**가 내부적으로 **infra-architect**, **restful-api-architect**, **senior-dba-advisor** 자동 조율
- 프론트엔드 개발: **frontend-senior-developer**가 내부적으로 **ux-design-advisor**, **restful-api-architect** 자동 조율
- 코드 품질: **senior-code-reviewer** → 피드백 반영 → 재검토
- 테스트: **test-scenario-architect** → **test-executor** → **senior-debugger** 순차 실행
